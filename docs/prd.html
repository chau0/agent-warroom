i PRD - Agent Warroom: AI Agents Debate My App Idea

Product Requirements Document

Agent Warroom: a web app where indie hackers enter one app idea and watch multiple AI agents debate whether it is worth building, technically feasible, growth-ready, or likely to fail.

Product Agent Warroom
Audience Indie hackers
MVP Goal Idea validation
Decision Output Build / Kill / Modify

1. Executive Summary

Agent Warroom helps solo founders and indie hackers avoid building weak ideas by simulating a structured startup debate among specialized AI agents. The user submits an app idea, then Founder, Engineer, Growth, and Skeptic agents independently evaluate it, criticize each other, and pass the full debate to a Judge agent for a final verdict.

The product should feel like a live startup warroom, but the underlying system must stay bounded, measurable, and useful. The main output is not entertainment. The main output is a concrete decision and next action.

Core positioning: Before you spend two weeks vibe-coding the wrong app, let five AI agents attack your idea first.

2. Problem Statement

Indie hackers often have too many app ideas and too little validation. With AI coding tools, building has become faster, but choosing what to build is still hard. Many builders waste days or weeks creating products with weak demand, unclear users, poor monetization, or hidden technical complexity.

Current pain points

  • Builders overestimate how good their ideas are.
  • They do not clearly define target users before coding.
  • They skip distribution thinking until after launch.
  • They underestimate technical complexity and maintenance cost.
  • They need honest pushback, not generic encouragement.

4. Goals and Non-Goals

Goals

  • Evaluate one idea through multiple expert perspectives.
  • Give a final Build / Kill / Modify recommendation.
  • Produce a useful next action, not just a score.
  • Make the experience feel like a live debate room.
  • Save and share validation reports.

Non-Goals

  • Do not become a general chatbot.
  • Do not allow unlimited agent debate loops in MVP.
  • Do not replace real customer interviews.
  • Do not perform deep market research in the first version.
  • Do not build complex agent memory in MVP.

5. Core User Journey

User opens homepage ↓ Enters app idea ↓ Clicks "Start Warroom" ↓ Round 1: agents generate independent opinions ↓ Round 2: agents critique each other ↓ Judge agent reviews transcript ↓ User receives verdict: Build / Kill / Modify ↓ User can save, share, export, or refine idea

6. MVP Scope

Must Have

  • Idea input form.
  • Four debate agents: Founder, Engineer, Growth, Skeptic.
  • One Judge agent.
  • Fixed two-round debate flow.
  • Final verdict with score and next action.
  • Basic animated debate UI.
  • Session persistence in local SQLite.
  • Shareable report page.

Should Have

  • Export report to Markdown.
  • Copy final recommendation.
  • Regenerate judge verdict.
  • Example ideas on homepage.
  • Basic usage limit by anonymous browser session or logged-in user.

Could Have

  • Competitor research agent.
  • Customer interview question generator.
  • Landing page generator based on the idea.
  • Multiple debate styles: friendly, brutal, investor-style, technical-only.

Out of Scope for MVP

  • Real-time multi-user collaboration.
  • Full agent memory system.
  • Payment and subscription billing.
  • Browser-based market research automation.

7. Agent Roles

Agent Responsibility Evaluation Focus
Founder Agent Evaluates whether this is worth building as an indie product. Pain, urgency, monetization, founder fit, MVP speed.
Engineer Agent Reviews technical feasibility and implementation complexity. Architecture, integrations, data, risk, time to MVP.
Growth Agent Reviews acquisition potential and distribution strategy. Channels, first users, virality, SEO, community, pricing.
Skeptic Agent Attacks weak assumptions and explains why the idea may fail. Demand risk, competition, unclear buyer, low willingness to pay.
Judge Agent Synthesizes debate and gives final recommendation. Final score, decision, strongest argument, biggest risk, next action.

8. Debate Flow

Round 1: Independent Opinions

Each non-judge agent receives only the original idea and scoring rubric. Agents must not see each other's responses yet. This prevents groupthink.

Round 2: Cross-Critique

Each agent receives the Round 1 transcript and must identify what other agents missed, where they agree, where they disagree, and whether their own position changed.

Round 3: Judge Verdict

The Judge receives the full transcript and returns a structured final decision.

Input Idea ↓ Founder | Engineer | Growth | Skeptic ↓ Independent JSON opinions ↓ Cross-critique round ↓ Judge synthesis ↓ Final report

9. Scoring Rubric

Criteria Weight Meaning
Pain Intensity 20 How painful and urgent is the user problem?

Willingness to Pay 15 Would users likely pay for this?

Technical Feasibility 10 Can an MVP be built without excessive complexity?
MVP Speed 10 Can a useful version be shipped quickly?
Competition Advantage 10 Is there a clear wedge or differentiation?

BUILD 80-100

The idea has strong pain, clear users, feasible MVP, and credible distribution.

MODIFY 55-79

KILL 0-54

The idea is too weak, unclear, crowded, expensive, or hard to validate.

11. Non-Functional Requirements

  • Latency: MVP response should complete within 30-60 seconds for a full debate.
  • Reliability: If one agent fails, the app should show partial results and retry only that agent.
  • Cost Control: Limit idea length, transcript length, max tokens, and number of rounds.
  • Security: All LLM API keys must stay server-side.
  • Observability: Log provider, model, token usage, latency, and error reason per agent call.
  • Backup: SQLite must be backed up daily using cron or a systemd timer.
  • Deployment: The app should run as a long-lived Node.js process behind Nginx or Caddy on Ubuntu.
  • Extensibility: Agent definitions should be configurable without rewriting orchestration logic.

12. Recommended Technical Stack

The MVP will be deployed on the user's own Ubuntu VPS. The stack should avoid managed SaaS dependencies where possible and use a simple local SQLite database. This keeps cost low, makes the system easy to understand, and fits a solo-builder deployment model.

Layer Choice Reason
Frontend Next.js App Router + React + Tailwind Fast MVP development, good UI structure, and one codebase for frontend and backend routes.
Backend Next.js Route Handlers running on Node.js Simple enough for the MVP. No separate backend service is needed at the beginning.
Database SQLite Best fit for a small self-hosted MVP. No external database server, low maintenance, easy backup, and enough for early traffic.
ORM / Query Layer Drizzle ORM or Prisma with SQLite Provides typed database access and migrations while keeping the schema simple.
LLM Layer Provider wrapper around Claude / GPT / Gemini APIs Keep the LLM provider replaceable. The app should call providers only from the server side.
Streaming Server-Sent Events or streaming Route Handler Creates a live debate feeling while staying simpler than WebSockets for the MVP.
Process Manager systemd or PM2 Keeps the Next.js Node server running after SSH disconnects or server restart.
Reverse Proxy Nginx or Caddy Handles HTTPS, domain routing, gzip/brotli, and proxying traffic to the Node.js app.
Deployment Ubuntu VPS + Git pull + build + restart script Simple, cheap, and under the builder's control. Good enough before introducing CI/CD.
Backup Scheduled SQLite backup using cron Copy the SQLite file daily to a backup directory or remote storage. This is critical because the database is local.

Recommended VPS Architecture

User Browser ↓ HTTPS Nginx / Caddy Reverse Proxy ↓ localhost:3000 Next.js Node Server ↓ SQLite database file ↓ Daily backup job

13. Data Model

-- SQLite schema

create table if not exists warroom_sessions (
  id text primary key,
  user_id text,
  idea text not null,
  status text not null default 'running',
  final_decision text,
  final_score real,
  final_summary text,
  created_at text not null default current_timestamp,
  updated_at text not null default current_timestamp
);

create table if not exists warroom_messages (
  id text primary key,
  session_id text not null,
  round integer not null,
  agent_key text not null,
  content text not null,
  score_json text,
  created_at text not null default current_timestamp,
  foreign key (session_id) references warroom_sessions(id) on delete cascade
);

create table if not exists agent_configs (
  id text primary key,
  agent_key text not null unique,
  name text not null,
  role_prompt text not null,
  is_active integer not null default 1,
  created_at text not null default current_timestamp
);

create index if not exists idx_warroom_messages_session_id
on warroom_messages(session_id);

create index if not exists idx_warroom_sessions_created_at
on warroom_sessions(created_at);

SQLite Notes

  • Generate UUIDs in the application layer and store them as text.
  • Store structured LLM outputs in score_json as JSON string text.
  • Use SQLite WAL mode for better read/write behavior on a small web app.
  • Keep the database file outside the Git repository, for example /opt/agent-warroom/data/warroom.sqlite.
  • Run daily backups before the app grows beyond a small solo-MVP workload.

19. Risks and Mitigations

Risk Impact Mitigation
Agents produce generic feedback. Product feels like a toy. Use strict rubric, role-specific prompts, and concrete next-action requirement.
LLM cost grows too quickly. Bad unit economics. Limit idea length, rounds, max tokens, and use cheaper model for critique.
Output is entertaining but not actionable. Low retention. Judge must always produce MVP scope and validation task.
Users distrust AI decision. Weak conversion. Show reasoning, disagreement, assumptions, and evidence gaps.
Too many similar tools appear. Low differentiation. Position specifically for indie hackers and AI-assisted builders.

22. Recommended First Build

Build the smallest useful version first: one page, one input, five hardcoded agents, one final report. Do not start with advanced multi-agent orchestration. The product will win or fail based on whether the final recommendation is sharp enough to change what the user does next.

First validation task: Build the MVP in 2-3 days, run 20 of your own app ideas through it, and publish the 5 most interesting warroom reports as public examples.
